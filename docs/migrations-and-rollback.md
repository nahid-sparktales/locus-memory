# Migrations, cutover and rollback

This document describes how `locus-memory` can take canonical ownership of memory records
from the Locus `MemoryVault` (`APP_DIR/memory/memory.sqlite3`, record format `memory-v1`)
and how ownership goes back to Locus. It covers requirements R19.1, R19.5, the ownership-related
parts of R19.2, and R20.1-R20.7 in [requirements.md](requirements.md). It does not cover the host
behaviour that R19.2-R19.4 and R19.6 require (no ingestion, maintenance, extraction or provider
calls in disabled mode; shadow comparison without prompt changes; enabled injection; fail-closed
behaviour). For that, see [handoff §4](../handoff/locus/README.md) and
[integration-locus.md](integration-locus.md). The
engine enforces only the context side of disabled mode (section 2): `MemoryEngine.ingest_event`,
`MemoryEngine.maintain` and the provider outbox do not read `serving_mode`. The legacy format
itself is described in
[locus-compatibility.md](locus-compatibility.md) §4, and the extraction stages are in
[ownership-and-extraction.md](ownership-and-extraction.md) and
[handoff/locus/README.md](../handoff/locus/README.md).

**Current state.** The ownership state machine, the migration tools and the rollback path are
implemented in `src/locus_memory/migrations/`. They are tested only on disposable copies of a
synthetic legacy vault. That vault was generated by the real Locus code at commit
`b332e4554e72956f949506207ffa034749360d79`
(`tests/fixtures/locus_legacy/make_fixture.py`, synthetic data, published test key).
**No real data has been migrated.** No cutover has run in Locus. Both host patches keep the
legacy vault canonical. Stage 1 has no ownership control. Stage 2 creates one
(`APP_DIR/memory-engine/control.sqlite3`) with no recorded transition, so it reads
`legacy_authoritative`. Neither patch has been applied to the real Locus checkout.

Code is cited by module and function or class name. The status labels mean:

- **implemented (tests: ...)**: the code exists, and the named tests exercise it.
- **implemented, untested**: the code exists, but no test exercises that particular path.
- **interface only**: a parameter or hook exists, and nothing in the package or the host
  supplies it.
- **not implemented**: a state or requirement exists, but no code path reaches it.
- **not executed**: the step needs a host change or real data, and neither has happened.

Test paths are relative to the repository root. Parametrized tests are named without their
parameter ids. Section 10 has the commands that run them.

## 2. The two rollout dimensions

R19.1 keeps two settings independent of each other.

| Dimension | Values | In the package | In Locus (Stage-2 patch, not applied to the real checkout) |
|---|---|---|---|
| Serving and learning mode | `disabled`, `shadow`, `enabled` | `host.EngineConfig.serving_mode`, validated in `EngineConfig.__post_init__`. Inside the engine only `disabled` changes behavior: `context.compiler.ContextCompiler.build` and `ContextCompiler.revalidate` return an empty packet with status `unavailable` (tests: `tests/test_context.py::test_serving_disabled_returns_unavailable_empty_packet`). The difference between shadow (compare only) and enabled (inject) is decided by the host. | `LOCUS_MEMORY_ENGINE_MODE` (default `disabled`) is read once per `ChatService` and passed as `EngineConfig(serving_mode=...)`. See [handoff §4](../handoff/locus/README.md). |
| Canonical backend and migration state | legacy or package, plus an ownership state per partition and record family | Enforced by `migrations.state.OwnershipControl`. A host is expected to pass it as `HostCapabilities.ownership` and to pass `OwnershipControl.writer_guard(...)` as the legacy vault's `write_guard`. The Stage-2 adapter does the former. No host code does the latter. `EngineConfig.canonical_backend` is only a label, reported by `status.py` as `EngineStatus.canonical_backend`. It is not derived from the ownership control. | `EngineConfig(canonical_backend="legacy")`. The control file at `APP_DIR/memory-engine/control.sqlite3` has no recorded transition, so the state reads `legacy_authoritative`, and package canonical writes raise `OwnershipFenced` (handoff §2, §5). |

These rules follow from the code:

- **Changing the serving mode never changes ownership.** Disabling serving does not move writes
  anywhere. In the disabled-mode test above, `remember` still succeeds while the context packet
  is empty.
- **Ownership changes only through `OwnershipControl.transition`, driven by
  `migrations.cutover.Migrator`.** No flag flips ownership. Once the package is authoritative,
  going back to legacy requires `Migrator.rollback` (R19.5).
- **Use the ownership state to answer "who owns writes".** That state comes from
  `MemoryEngine.ownership_state`. In the CLI, use `locus-memory --admin migrate state`, or the
  `ownership:` line of `locus-memory status`. The `ownership:` line appears only after a
  migration transition has been recorded for the profile (`cmd_status` prints it only when
  `MemoryEngine.ownership_state` is not None, and `cli.Session.engine` wires the control only
  for generation > 0). Before that, `migrate state` reports `recorded: false`. The standalone
  CLI builds the engine with the default `EngineConfig`, so `status` always prints
  `backend / serving: package / enabled`, even when the ownership line says
  `legacy_authoritative`.
- **Fencing is opt-in.** If a host builds the engine without `HostCapabilities.ownership`, or
  builds the legacy vault without `write_guard`, nothing is fenced. The CLI wires the
  engine-side fence only for a profile whose ownership row has at least one recorded transition
  (generation > 0, in `cli.Session.engine`).

## 3. Ownership state machine (`migrations/state.py`)

### 3.1 Storage and transitions

- **File.** The control file is `<root>/control.sqlite3`, opened through
  `storage.db.Database`: WAL, `synchronous=FULL`, file mode 0600, writes in `BEGIN IMMEDIATE`.
- **Tables.**
  - `ownership(partition_id, family, state, generation, updated_at, details)`
  - `ownership_log(id, partition_id, family, from_state, to_state, generation, at, reason)`,
    where `id` is an `INTEGER PRIMARY KEY AUTOINCREMENT` that `OwnershipControl.history` orders by
- **Contents.** The file is content-free and **not encrypted**. It holds partition ids, states,
  timestamps, a reason string (cut to 200 characters) and the `details` JSON. The details
  include, for example, the snapshot directory path and the row counts.
- **Key and families.** Each row is keyed by (security partition, record family). The families
  are `memories`, `context_snapshots` and `skill_observations` (`state.FAMILIES`). `Migrator`
  handles only `memories` (`Migrator.FAMILY`). A partition and family with no row reads as
  `legacy_authoritative`, generation 0 (`OwnershipControl.get`).
- **Transitions.** `OwnershipControl.transition(partition_id, family, target,
  expected_generation=..., reason=...)` works inside one write transaction:
  1. It reads the current row.
  2. It rejects a stale `expected_generation` with `RevisionConflict`. This compare-and-swap
     stops two migrators from both advancing the state.
  3. It rejects a target that is not in `TRANSITIONS` with `ValidationError`.
  4. It writes `generation + 1`, merges the `details`, and appends a log row.

  Tests: `tests/test_migrations.py::test_illegal_transitions_and_concurrent_migrators`.
- **History.** `OwnershipControl.history` returns the log. The CLI prints it with
  `migrate state`.

### 3.2 States

"Writers" means the permitted writers, from `state.WRITERS`.

| State | Authoritative owner | Writers | Crash recovery (as implemented) | Allowed transitions (`state.TRANSITIONS`) | Code path that performs each transition |
|---|---|---|---|---|---|
| `legacy_authoritative` | legacy | legacy | Not applicable. A crash inside `prepare_shadow` leaves this state; run `prepare_shadow` again. It writes a new snapshot directory, and the import is idempotent. | `shadow_prepared` | `Migrator.prepare_shadow` |
| `shadow_prepared` | legacy | legacy | Run `validate` again: it re-imports the delta from the live file and re-verifies. A failed verify stays in this state. | `validated`, `legacy_authoritative` | `Migrator.validate`. The move back to `legacy_authoritative` is permitted, but no Migrator method or CLI command performs it. |
| `validated` | legacy | legacy | Proceed to cutover, or abort to legacy. Verify can be re-run read-only. | `cutover_in_progress`, `shadow_prepared`, `legacy_authoritative` | `Migrator.cutover`; `cutover.abort_cutover`. The move back to `shadow_prepared` is permitted but unused. |
| `cutover_in_progress` | none (quiesced) | none | `Migrator.resume` finishes the cutover (final delta, verify, transition), or aborts to legacy on any failure. `abort_cutover` needs no legacy file; with the partition context (Migrator, CLI) it first applies package deletions made since the fence to the legacy file. | `package_authoritative`, `legacy_authoritative` | `Migrator._finish_cutover`, `abort_cutover` |
| `package_authoritative` | package | package | Not applicable | `rollback_in_progress`, `legacy_retired` | `Migrator.rollback`. The move to `legacy_retired` is permitted, but no code path performs it. |
| `rollback_in_progress` | none (quiesced) | none | `Migrator.resume` finishes the reverse sync with the recorded `allow_partial`. No abort back to the package exists. | `legacy_authoritative`, `package_authoritative` | `Migrator._finish_rollback`. The move back to `package_authoritative` is permitted but unused. |
| `legacy_retired` | package | package | Terminal | none | Not reachable (not implemented) |

The `migrations.state` module docstring says the reverse sync is in `migrations.rollback`. It is
actually in `migrations.cutover.Migrator`.

These `details` keys are recorded on each transition:

| Transition into | `details` keys |
|---|---|
| `shadow_prepared` | `snapshot_dir`, `snapshot_rows` |
| `validated` | `verified_records` |
| `package_authoritative` | `cutover_at` |
| `rollback_in_progress` | `allow_partial` |
| `legacy_authoritative` (after a rollback) | `package_readonly_recovery`, `rolled_back_at` |

### 3.3 Where writers are fenced

- **Legacy writer.** A host fences it by building
  `compat.legacy_vault.LegacyMemoryVault(..., write_guard=control.writer_guard(pid, "memories",
  "legacy"))`.
  - Every record mutation (`save`, `approve`, `delete`, `delete_all`, `feedback`,
    `expire_candidates`, `maintain`) runs in `compat.legacy_vault._guarded_write`. That function
    takes `BEGIN IMMEDIATE` on the legacy file and then calls the guard inside the transaction.
  - Read-path side effects (cached-vector reseals in `LegacyMemoryVault._store_embedding`,
    the `use_count`/`last_used_at` update in `search`, and `memory_events` inserts in
    `record_event`) are skipped while fenced, but are checked only up front
    (`LegacyMemoryVault._side_effects_allowed`), outside a guarded transaction. One that passed
    the check just before the fence can still commit after it. They change no revision,
    status, scope, target or fingerprinted column.
  - While fenced, the vault serves reads without candidate-expiry deletes, use-count updates,
    cached-vector writes or diagnostics events (subject to the up-front check above).

  Tests: `tests/test_compat_legacy.py::test_write_guard_fences_mutations_but_not_reads`,
  `tests/test_compat_legacy.py::test_fenced_reads_never_modify_the_store`,
  `tests/test_migrations.py::test_full_cutover_fences_legacy_writer`.
- **Package writer.** Two checks guard canonical writes:
  - `MemoryEngine._fence` checks up front, in every engine API that writes canonical records
    (memories, episodes, procedures, repository observations, summaries).
  - `CoreService._check_owner` checks again inside the write transaction, for writes that go
    through `CoreService` (`CoreService._commit_write`).

  A `CoreService` write that passed the first check just before a migrator fenced the package
  cannot commit afterwards. Tests: `tests/test_migrations.py::test_engine_canonical_writes_are_fenced_until_package_is_authoritative`,
  `tests/test_review_group1.py::test_canonical_record_writes_are_fenced_beyond_the_core_api`,
  `tests/test_review_group1.py::test_a_write_that_passed_the_fence_before_rollback_is_fenced_not_lost`.
- **Migration writes: the inverse fence.** The importer's writes (`imported`, `legacy_delta`) are
  permitted only while the legacy store is the authority (`legacy_authoritative`,
  `shadow_prepared`, `validated`) or during the Migrator's own final delta (`cutover_in_progress`,
  under its legacy write barrier); a rollback's adoption of written-back records
  (`legacy_adopted`) only in `rollback_in_progress`. `CoreService._check_migration_state` checks
  this inside the write transaction (`core._MIGRATION_CHANGES`), and `LegacyImporter` refuses up
  front with `OwnershipFenced` (it never re-imports over an authoritative package store). The
  cutover's final transition holds the package store's write lock, so an importer that checked the
  state just before it cannot commit after it. Tests:
  `tests/test_review_round2_batch1.py::test_hc2_the_importer_refuses_after_cutover_and_a_correction_is_kept`,
  `::test_hc2_migration_writes_are_fenced_inside_the_transaction`.
- **Not fenced, by design.**
  - Deletion-driven rewrites (`core._UNFENCED_CHANGES`: `source_forgotten`, `evidence_revoked`).
  - Forgetting (`MemoryEngine.forget`), so that a user can always forget. A deletion the importer
    propagates (section 4.5) re-checks the ownership state under the package write lock just
    before its ledger append.
- **Not fenced, outside the canonical-record scope.** The fence covers canonical memory records
  only. Other engine writes do not call `MemoryEngine._fence`, for example
  `MemoryEngine.ingest_event` (the session-history archive) and
  `MemoryEngine.register_repository`. Section 4.12 describes what this means for a rollback.
- **Maintenance.** `learning.consolidation.ConsolidationService.maintain` skips persisted
  lifecycle transitions when the package is not a permitted writer
  (`ConsolidationService._package_writes_allowed`). In that case it reports
  `lifecycle_maintenance: "fenced"`. Tests:
  `tests/test_review_group1.py::test_maintenance_never_rewrites_records_owned_by_the_legacy_store`.
- **The migrator itself.** During `rollback_in_progress` no writer is permitted. The reverse sync
  writes the legacy file through an unguarded `LegacyMemoryVault` that `Migrator._finish_rollback`
  creates for this purpose.

There is no dual-write. At every state, at most one writer is permitted.

## 4. Protocol

| Step | Library | CLI (section 6) | State change |
|---|---|---|---|
| 1. Inventory (dry run) | `legacy.inventory` | `migrate inventory` | none |
| 2. Snapshot and manifest | `legacy.snapshot`, `legacy.verify_snapshot` | `migrate snapshot` | none |
| 3. Shadow import | `Migrator.prepare_shadow`: a snapshot, then `LegacyImporter.run` on that snapshot | `migrate import` | `legacy_authoritative` -> `shadow_prepared` |
| 4. Validate | `Migrator.validate`: a delta import from the live file, then `legacy.verify` | `migrate verify` (in `shadow_prepared`) | -> `validated`, only when verify passes |
| 5. Cutover | `Migrator.cutover` | `migrate cutover --yes` | `validated` -> `cutover_in_progress` -> `package_authoritative`, or back to `legacy_authoritative` on failure |
| 6. Resume or abort | `Migrator.resume`, `cutover.abort_cutover` | `migrate cutover --yes` or `migrate rollback --yes` in an in-progress state; `migrate abort --yes` | finishes, or aborts |
| 7. Rollback | `Migrator.plan_rollback`, `Migrator.rollback` | `migrate rollback [--allow-partial] --yes` | `package_authoritative` -> `rollback_in_progress` -> `legacy_authoritative` |

`Migrator` and `LegacyImporter` refuse an `AccessContext` without `Operation.ADMIN`.
`inventory` and `snapshot` take no access context. Nothing runs when the package is imported or
installed (R20.1).

### 4.1 Inventory (dry run)

`legacy.inventory(legacy_db, key, mapping)` opens the legacy file through a read-only SQLite URI
(`mode=ro`). It decrypts each row in memory to classify it, and returns counts only:

- rows and columns;
- counts by `scope:status`;
- the lifecycles the rows map to;
- decrypt and map failures;
- unmapped scopes, and the policy that applies to them;
- each unsupported field, with its record count and how it is handled;
- row counts of the tables that are not migrated;
- the candidate policy: candidates stay candidates, and expired ones import as expired.

It needs no package vault. Tests:
`tests/test_migrations.py::test_inventory_is_read_only_and_content_free`,
`tests/test_migrations.py::test_inventory_reports_unmapped_scopes_and_wrong_key`,
`tests/test_cli.py::test_migrate_inventory_reports_counts_only`.

### 4.2 Snapshot and manifest

`legacy.snapshot(legacy_db, out_dir)` makes the snapshot:

- **The copy.** It uses SQLite's online-backup API from a read-only source connection and writes
  `out_dir/legacy-snapshot.sqlite3` (journal mode DELETE, file mode 0600).
  - The copy holds the same ciphertext and the same plaintext metadata columns as the source,
    including the content-free `memory_events` table.
  - Nothing is decrypted, and no key is needed.
- **The manifest.** `manifest.json` records:
  - format `locus-memory.legacy-migration-manifest`, version 1;
  - source format `locus-memory-vault:memory-v1`;
  - destination schema;
  - creation time and row count;
  - a fingerprint for each row (section 4.4);
  - the snapshot's SHA-256 and file name.

  The manifest contains row ids and fingerprints and no content. It is written with the
  process umask; there is no explicit chmod.
- **No overwrite.** It refuses a directory that already holds a snapshot.

`legacy.verify_snapshot(out_dir)` re-hashes the copy against the manifest. It is a library
function with no CLI command, and `prepare_shadow` does not call it before importing. Tests:
`tests/test_migrations.py::test_snapshot_manifest_integrity_and_no_plaintext`.

### 4.3 Shadow import

`Migrator.prepare_shadow` requires `legacy_authoritative`:

1. It writes a snapshot under `<work_dir>/snapshot-<epoch milliseconds>/`.
2. It runs `LegacyImporter.run` against the snapshot, never against the live file.
3. It moves to `shadow_prepared`.

`legacy.LegacyImporter.run` works in this order:

0. It refuses with `OwnershipFenced` unless the legacy store is the authority (section 3.3): the
   state is read from the `ownership` control the Migrator passes, and from the engine host's.
1. It reads every legacy row through a read-only connection, ordered by `created_at` and `id`.
2. `LegacyImporter._preflight` checks the ids before any batch commits. It raises
   `MigrationError` if a legacy id is already used by a package record that is neither a legacy
   import nor a record written back by an earlier rollback (`legacy._legacy_origin`).
3. Rows are processed in batches, 200 per write transaction by default. Each row is decrypted
   and mapped (`legacy.map_record`, section 5). Then one of three things happens:
   - **New in the package:** it is inserted with change `imported`, after
     `legacy.forgotten_check` (section 4.6).
   - **Unchanged:** it is counted `unchanged`.
   - **Changed:** it is rewritten as a delta (section 4.4) with change `legacy_delta`. The write
     is compare-and-swap on the package revision.

   Decrypt and map failures are counted, not raised. `verify` reports the rows they affect.
4. Legacy deletions are propagated (section 4.5).

The report can contain these keys: `rows`, `imported`, `unchanged`, `updated`,
`metadata_deltas`, `rescoped`, `drift_repaired`, `skipped_forgotten`, `decrypt_failures`,
`map_failures`, `deleted_in_legacy`, `deletion_propagation` and `notes`. Only `rows`,
`deleted_in_legacy`, `deletion_propagation` and `notes` are always present. The other counts
come from a `Counter`, so a count key is present only when it is non-zero (the tests read them
with `report.get("imported", 0)`). The `notes` count normalizations such as
`unmapped_scope`, `embedding_dropped` and `timestamp_milliseconds_normalized`.

**Idempotent and resumable.** A re-run inserts nothing new and counts every row as `unchanged`.
An import interrupted between batches resumes on the next run. Tests:
`tests/test_migrations.py::test_import_preserves_identity_lifecycle_scope_and_is_idempotent`,
`tests/test_migrations.py::test_import_interrupted_mid_batch_resumes`.

### 4.4 Fingerprints and deltas

Three different fingerprints exist. Only the second one drives deltas.

| Fingerprint | Computed by | Covers | Stored in | Used for |
|---|---|---|---|---|
| Manifest row fingerprint | `legacy._row_fingerprint` (SHA-256) | id, status, scope, target_hash, revision, nonce, ciphertext | `manifest.json` (plaintext, content-free) | A record of the snapshot. The importer does not read it. |
| Legacy metadata fingerprint | `legacy.legacy_fingerprint` (SHA-256 with the domain prefix `locus-memory/legacy-fingerprint/v1\|`) | revision, status, stale, superseded_by, pinned, expires_at, target_hash, scope | `extra.legacy_fingerprint`, inside the encrypted package record | Delta detection and verification |
| Adapter change gate | Stage-2 host adapter (`memory_adapter.py` in patch 0002, not part of the package) | ids, revisions, flags, targets, nonces (no ciphertext) | memory only | Skipping the import when nothing changed (handoff §2) |

**Why the metadata fingerprint is needed.** The legacy vault changes some columns in place,
without bumping `revision` ([locus-compatibility.md](locus-compatibility.md) §4.11):

- `stale`, set by feedback `incorrect` and by `maintain()`;
- `stale` and `superseded_by`, set by `approve(resolution="replace")` on the conflicting rows.

`pinned` and `expires_at` are different. They are not bound by the AAD
([locus-compatibility.md](locus-compatibility.md) §4.4), so a direct edit of the file can change
them without a revision bump. No `MemoryVault` method does this: they are set only by `save()`,
which bumps the revision. The fingerprint covers them anyway. (The test
`tests/test_migrations.py::test_verify_compares_metadata_changed_without_revision_bump` edits
them with direct SQL.)

The legacy revision alone therefore cannot detect every change.

`legacy.delta_reasons(existing, mapped)` returns the reasons an imported record must be
re-imported:

- **`revision`:** the legacy revision differs from `extra.legacy_revision`.
- **`metadata`:** the revision is the same, but the fingerprint differs. This also applies when
  the stored record has no fingerprint, because it was imported before fingerprints existed. Such
  a record is re-imported once. `verify` treats a missing fingerprint as unknown, not as a
  mismatch.
- **`scope`:** the host mapping now maps the legacy target to a different package scope. The
  record is re-scoped, and the authorization index moves with it.
- **`drift`:** none of the above applies, but the package copy differs from the mapped legacy
  row. One example: maintenance persisted an expiry while the engine had no ownership control.
  The legacy row wins.

A delta writes a new package revision (`existing.revision + 1`). The new legacy revision goes
into `extra.legacy_revision`. Package and legacy revisions are therefore equal only until the
first delta. Citations that were forgotten in the package stay dropped.

**A delta never drops package-only provenance** (`legacy.merge_delta`). The fields the legacy
format carries (kind, lifecycle, scope, title, content, tags, reason, validity, retention,
supersedes/superseded_by, created/updated time, `legacy_*` bookkeeping) come from the legacy row.
Citations the legacy row does not produce (memory, message, session, episode or task-attempt
evidence) and `links.derived_from` are kept, so forgetting an input still cascades to the record.
A package record a rollback wrote back (`extra.legacy_round_trip`) additionally keeps its statement
basis, its conflict links and its other `extra` entries, and never becomes an "imported" record.
`verify` therefore does not compare a written-back record's basis, nor any record's
`derived_from` (section 4.7). Tests:
`tests/test_review_round2_batch1.py::test_fg2_round_trip_keeps_provenance_so_forgetting_an_input_cascades`,
`::test_fg2_a_legacy_edit_of_a_written_back_record_keeps_its_provenance`.

These legacy changes are **not deltas**: feedback `helpful`/`ignored`, `use_count` and

### 4.5 Deletion propagation

After every import, `LegacyImporter._propagate_deletions` looks for imported records whose legacy
row is gone (`legacy._orphaned_legacy_records`):

- A readable record of legacy origin (`legacy._legacy_origin`) is a target: imported
  (`extra.legacy`) or written back by a rollback (`extra.legacy_round_trip`). A package-native
  record that never reached the legacy store has neither marker and is never forgotten for being
  absent there.
- A record that no longer authenticates counts only if the source index shows it was a legacy
  import. Its scope is unreadable, so it cannot be forgotten through that scope, and every run
  reports it as a failure.

For each target, the importer:

1. inserts a `migration_forgets` row (record id, generation still NULL);
2. calls `ForgettingService.forget` with `ForgetTarget("memory", id)` and
   `ForgetPolicy(suppress_relearning=False)`. The access context comes from
   `LegacyImporter._forget_access`: same principal and partition, actor `HOST`, operations
   `{FORGET, ADMIN}`, and grants equal to the record's own scope values, never wider;
3. binds the `migration_forgets` row to the tombstone's deletion generation.

When a forget fails:

- the failure is counted by error code in `deletion_propagation.failed_by_code`;
- the record stays, and the run continues;
- `verify` reports `deleted_in_legacy` for it, so validation and cutover cannot pass;
- the next run retries it.

The `migration_forgets` table is part of the partition schema (`storage/schema.py`). It separates
a propagated legacy deletion from a user's forget:

- If a legacy row comes back under the same id (for example, the user restores a legacy export),
  it is new legacy data and is imported again.
- A user's forget is never undone.

**Records written back by a rollback.** A user's legacy-side deletion of a written-back record
(`extra.legacy_round_trip`) is propagated like any other legacy deletion, and `verify` reports it
as `deleted_in_legacy` until it is. Tests:
`tests/test_review_round2_batch1.py::test_fg4_a_legacy_deletion_of_a_written_back_record_is_propagated`,
`::test_fg4_a_package_native_record_absent_from_legacy_is_never_forgotten`.

### 4.6 Tombstone non-resurrection

Before it inserts a legacy row that has no package record, the importer calls
`legacy.forgotten_check`. The row is skipped (counted `skipped_forgotten`) in any of these cases:

- **Memory tombstone.** A memory tombstone exists for the id, unless that tombstone only
  propagated a legacy deletion (`legacy._migration_forget`). Every record a forget removes besides
  its own target gets one (policy `{"derived":true}`, never adopted into the ledger): records
  removed by cascade, with their evidence (a source, session or cited record forgotten), as a
  forgotten attempt's dependents, and records of legacy origin (imported, or written back by a
  rollback) that a scope or profile forget removes. Such a record is never re-imported as new
  legacy data, whatever its legacy row says (including its unauthenticated `created_at`). Tests:
  `tests/test_review_round3_batch1.py::test_mf3_remigration_never_reimports_a_cascade_removed_written_back_record`,
  `::test_mf3_an_imported_record_removed_with_its_evidence_is_never_reimported`,
  `::test_rg1_a_created_at_edit_never_undoes_a_scope_or_profile_forget`.
- **Forgotten import source.** The record's `LEGACY_IMPORT` source (`legacy_import:legacy-vault:<id>`)
  was forgotten. A forgotten *secondary* source (a session or run reference) is dropped instead,
  and the row is still imported.
- **Suppression or forgotten evidence.** `ForgettingService.blocked_reason` reports a
  suppression, a forgotten derivation input or a missing evidence episode.
- **Scope or profile forget that covers the row** (`legacy._scope_forget_reason`). A forget of a
  scope value of the mapped scope (project, agent, ...) or of the profile covers the legacy rows
  that existed when it ran, never every later row:
  - a forget at or below the last rollback's deletion generation (`legacy.rollback_watermark`,
    recorded by `_finish_rollback`) was applied to the legacy store by that rollback, so a row
    present now was written afterwards and is imported;
  - a later forget covers a row created at or before the tombstone's time (ledger, records and
    the legacy vault use the host clock), even if it was edited later; a row created after it is
    new legacy data and is imported. A row dated later than now fails closed (covered). This rule
    only decides for legacy ids the package never held: `created_at` is a plaintext column outside
    the legacy ciphertext's authentication, so a keyless edit can still move a never-imported row
    between "before" and "after" the forget.

`verify` uses the same decision: a skipped row is forgotten, any other absent row is `missing`.
Rollback deletes the legacy rows the last cutover verified whose package record is gone, and a
legacy row the package never held only when a package forget covers it (section 4.11), so a later
migration has nothing to bring back. The exceptions are rows the rollback keeps: rows whose
package record no longer authenticates, and legacy rows that do not decrypt. Tests:
`tests/test_review_round2_batch1.py::test_fg1_legacy_memory_created_after_a_forget_survives_remigration_and_rollback`,
`::test_fg1_a_scope_forget_covers_only_legacy_rows_written_before_it`,
`::test_fg1_rollback_never_deletes_a_legacy_row_the_package_never_held`.

Tests:

### 4.7 Verify

`legacy.verify(engine, access, legacy_db, key, mapping, queries=...)` checks three things.

**Every legacy row.**

1. Decrypt it. A failure is an `undecryptable` mismatch.
2. Map it. A failure is `unmappable`.
3. Read the package record, which decrypts and authenticates it. A record that is absent and not
   covered by a forget is `missing`.
4. Compare `kind`, `lifecycle`, `scope`, `title`, `content`, `tags`, `basis` (not for a record a
   rollback wrote back, which keeps its own), `created_at`, `updated_at`, `validity` and
   `extra.legacy_revision`.
5. Compare the metadata the legacy vault edits in place (`pinned`, `expires_at`, retention
   policy, `superseded_by`, `supersedes`; conflict links of imported records) and, when one is
   stored, the metadata fingerprint. `derived_from` is package provenance and is not compared.

**Every imported record whose legacy row is gone.** The selection is the same as in section 4.5
(`legacy._orphaned_legacy_records`): readable records of legacy origin (imported or written
back), and unreadable ones that the source index shows as legacy imports. Each one is a mismatch:
`deleted_in_legacy`, or `unreadable` if the record no longer authenticates.

**Retrieval behavior, once per `query`.** Verify compares membership, not ranking. One side is the
set of approved legacy rows that a simplified lexical matcher selects
(`legacy._legacy_search_ids`). This matcher is not Locus's ranking or semantic recall. It
selects every approved row that matches, regardless of scope, target or the caller's grants, and
includes stale, superseded and validity-ended rows. The other side is the hit set of
`engine.search` under the caller's access, which is grant-filtered. So `legacy_hits` and
`package_hits` are not comparable for scoped records. The result holds counts and a
12-character hash of the query. It does not affect `ok`.

The result has these keys: `ok` (true when there are no mismatches), `checked`, `missing`,
`mismatches` and `behaviour`. Each mismatch is an id and a field name, with no content, and at
most 200 are returned. Tests:
`tests/test_migrations.py::test_verify_compares_metadata_changed_without_revision_bump`,
`tests/test_review_group1.py::test_a_corrupt_row_fails_validation_without_raising`.

### 4.8 Validate

`Migrator.validate` requires `shadow_prepared`. It imports the delta from the live legacy file
through a read-only connection, then runs `verify`. When verify passes, the state moves to
`validated`. Otherwise the state stays `shadow_prepared` and the report is returned. Legacy writes
made during the shadow phase are picked up here. Tests:
`tests/test_migrations.py::test_full_cutover_fences_legacy_writer`.

### 4.9 Cutover, quiesce hook and write barrier

`Migrator.cutover(quiesce=None, queries=None)` proceeds as follows:

1. **Fence.** It requires `validated`, then moves to `cutover_in_progress`. From this durable
   state change on, no writer is permitted.
2. **Quiesce and barrier.** `Migrator._finish_cutover` enters `quiesce()` if the host passed one.
   It then enters `Migrator._legacy_write_barrier`, which opens the legacy file with `mode=rw`
   (so it never creates a file) and holds `BEGIN IMMEDIATE` until the end of the step.
3. **Final delta.** It imports the final delta from the live file, then runs `verify`.
4. **Decide.**
   - If verify fails, the state moves to `legacy_authoritative` and the result says
     `cutover: false`. Nothing is raised. This is also what happens with a wrong key or a
     malformed or undecryptable row: `LegacyImporter.run` counts them as `decrypt_failures` or
     `map_failures`, and `legacy.verify` reports `undecryptable` or `unmappable` mismatches.
     The undecryptable-row case is tested
     (`tests/test_review_group1.py::test_cutover_with_a_corrupt_row_aborts_instead_of_wedging`).
     The wrong-key case takes the same code path but has no cutover test.
   - If verify passes, the legacy ids it verified are recorded as the **cutover set** (keyed
     tokens in the partition table `migration_cutover_ids`; `legacy.record_cutover_set`), and the
     state moves to `package_authoritative` while the package store's write lock is held (an
     importer that checked the state just before cannot commit after it, section 3.3). The
     legacy file's path is recorded in the ownership details (`legacy_db`).
   - After the barrier is released, `cutover.propagate_forgets_to_legacy` removes the snapshot
     directories this migration wrote (`snapshot_dirs`) and deletes from the live legacy vault
     every row of the cutover set without a package record (forgotten in the package while
     legacy was authoritative). The result reports it as `legacy_residue`.
5. **Abort on an exception.** Any exception before the final transition moves the state back to
   `legacy_authoritative` and is re-raised. Examples: a missing, moved or unreadable legacy file
   (SQLite errors); a failing `quiesce` hook; a `MigrationError` such as a non-legacy id clash
   in `LegacyImporter._preflight`. No package canonical write is accepted before the final
   transition, so aborting loses nothing.

**How the barrier works.** A guarded legacy writer re-checks its guard inside its own
`BEGIN IMMEDIATE` transaction. So a write that passed the guard just before the fence ends one of
two ways:

- it commits before the migrator gets the lock, and its row is in the final delta; or
- it is fenced (`OwnershipFenced`).

Tests: `tests/test_review_group1.py::test_a_fence_passed_legacy_write_is_fenced_or_migrated_never_lost`.

**Quiesce hook: interface only.** `quiesce` is a zero-argument callable. Its return value is used
as a context manager around the barrier, the final delta, verify and the final transition. Its
purpose is to let the host drain in-flight turns and REST writes. No test passes a hook, the CLI
never passes one, and no host implementation exists (handoff §9, item 2). Without a hook, cutover
relies on the write barrier and on every legacy writer being guarded.

**Precondition: every legacy writer is guarded.** A writer built without `write_guard` is never
fenced. That includes every Locus code path that writes the vault, both at the inspected commit
and with the Stage-1 facade, which does not pass `write_guard`. After cutover, such a writer's
changes land only in the legacy file and are never imported:

- New rows: a later rollback keeps them (`legacy_only_kept`), unless a package forget covers
  them, because `Migrator._delete_gone` deletes only rows of the cutover set (or covered by a
  package forget) for lack of a package record.
- Edits to existing rows: a later rollback overwrites them with the package version, because
  `Migrator._write_back` saves any record whose legacy row differs.
- Deletions of existing rows: a later rollback restores the row from the package.

This follows from reading the code; no test covers an unguarded writer during cutover. Handoff
§9 item 2 requires wiring `OwnershipControl.writer_guard` into the legacy vault before the
cutover is run.

**Forgets after cutover reach the copies kept for rollback.** The live legacy vault stays on disk
as the rollback target, decryptable with the legacy key the host keeps. After every forget (and on
every open, and at cutover) `ForgettingService.propagate_to_migration_copies` runs
`cutover.propagate_forgets_to_legacy` while the package is authoritative: rows of the cutover set
whose package record no longer exists are deleted by id (no key needed) under the legacy file's
write lock with `secure_delete`, then the legacy WAL is truncated, and any leftover recorded
snapshot is removed. It is driven by the deletion generation (partition meta
`legacy_residue_generation`), so a crash or a busy legacy file only delays it. Until it succeeds
the forget's receipt sets `physical_purge_pending` and carries a limitation naming the copies kept
for rollback. Rollback still works: it reverse-syncs from the package store. Tests:
`tests/test_review_round2_batch1.py::test_cd1_forget_after_cutover_leaves_no_legacy_or_snapshot_copy`,
`::test_cd1_a_busy_legacy_store_is_reported_and_finished_later`,
`::test_cd1_cutover_applies_forgets_made_while_legacy_was_authoritative`.

Redirecting the host's reads and writes to the package at cutover (R20.5) is host work, and it is
not implemented.

Tests:

### 4.10 Crash recovery, resume and abort

`Migrator.crash_at` is a test hook: it raises `SimulatedCrash` at the named point, which models
the process dying there.

| Crash point | State left | Recovery | Test |
|---|---|---|---|
| `after_snapshot` | `legacy_authoritative` | Run `prepare_shadow` again. It writes a new snapshot directory. | `tests/test_migrations.py::test_crash_during_shadow_leaves_legacy_authoritative` |
| `after_shadow_import` | `legacy_authoritative` | Same as above | same test |
| Between import batches (`LegacyImporter.after_batch`) | unchanged | Run the import again. Committed batches count as `unchanged`. | `tests/test_migrations.py::test_import_interrupted_mid_batch_resumes` |
| `after_fence` | `cutover_in_progress`, no writers | `resume`, or `abort_cutover` | `tests/test_migrations.py::test_crash_during_cutover_resumes_without_losing_writes`, `tests/test_review_group1.py::test_an_unresumable_cutover_can_be_aborted` |

| `before_authoritative` | `cutover_in_progress` | `resume` | same test |
| `after_rollback_fence` | `rollback_in_progress` | `resume` | none: the point exists in `Migrator.rollback` but is untested |
| `after_reverse_sync` (legacy written, package transaction not committed) | `rollback_in_progress` | `resume` | `tests/test_review_round3_batch1.py::test_mf1_a_forget_between_a_crashed_rollback_and_resume_reaches_the_legacy_copy` |
| `before_rollback_complete` (package committed, transition not made) | `rollback_in_progress` | `resume` | `tests/test_migrations.py::test_crash_during_rollback_resumes`, `tests/test_review_round3_batch1.py::test_mf4_a_crash_around_the_transition_never_loses_the_adoption_or_watermark` |

`Migrator.resume(quiesce=None)` acts on the recorded state:

- `cutover_in_progress`: it runs `_finish_cutover` again, without retrieval queries.
- `rollback_in_progress`: it runs `_finish_rollback` again, with the recorded `allow_partial`.
- `legacy_authoritative` after a rollback whose package transaction was lost (an earlier build
  made the transition inside that transaction, so a crash or failed commit after it left legacy
  authoritative without the adoptions and the watermark): the control record's
  `rollback_deletion_generation` is above the package's recorded watermark, or no watermark was
  recorded. `Migrator._repair_rollback_commit` adopts the package-native records whose ids are in
  the legacy file (change `legacy_readopted`, permitted only in `legacy_authoritative`) and records
  the watermark; it returns `resumed: true` with `repaired_rollback`. `prepare_shadow` runs the
  same repair first. Test:
  `tests/test_review_round3_batch1.py::test_mf4_resume_repairs_a_rollback_whose_package_commit_an_earlier_build_lost`.
- Any other state: it returns `resumed: false`.

`cutover.abort_cutover(control, partition_id, reason)` moves `validated` or `cutover_in_progress`
to `legacy_authoritative` and needs no legacy file. Resuming without the legacy file also ends in
`legacy_authoritative`: `_finish_cutover` aborts by itself, and the barrier never creates an empty
file where the legacy vault belongs. Tests:
`tests/test_review_group1.py::test_an_unresumable_cutover_can_be_aborted`,
`tests/test_review_group1.py::test_cli_migrate_abort_and_cutover_fallback`.

**Forgets while a cutover is in progress.** Forgetting is never fenced, so a forget made in
`cutover_in_progress` is applied to the package store while the legacy file still holds the row.
`cutover()` records the deletion generation at the fence (`fence_generation`) and the legacy file.
Every abort with the partition context - `Migrator.abort_cutover`, `_finish_cutover`'s abort on a
failed verify or on any other failure, and the CLI `migrate abort` when the vault opens - first
deletes from the legacy file (by id, `secure_delete`, then a truncating checkpoint) the rows of
every record a package deletion removed since the fence (`legacy.forgotten_since`), under the
package write lock and the ledger's write lock held until the transition, exactly like a
rollback's last step. The result reports `legacy_deletions` (`deleted`, `complete`); a missing or
busy legacy file never blocks the abort. The receipt of such a forget says what happens to the
legacy copy (`forgetting._CUTOVER_PENDING`). Tests:
`tests/test_review_round3_batch2.py::test_mf5_a_forget_during_cutover_reaches_the_legacy_store_when_the_cutover_aborts`,
`::test_mf5_an_abort_without_the_partition_context_still_happens_and_the_receipt_said_so`.

No abort exists for an interrupted rollback. `TRANSITIONS` permits
`rollback_in_progress -> package_authoritative`, but no code path uses it.

**R20.4 is only partly covered.** R20.4 asks for interruption tests at every boundary. Crash
points exist only at the points in the table above. There is none in `validate` (between its
delta import and its verify), none between taking the cutover barrier and the final delta, none
inside deletion propagation (between the `migration_forgets` mark, the forget and the binding),
and none inside the reverse sync before `before_rollback_complete`. Besides
`after_rollback_fence`, those boundaries are untested.

**A rollback interrupted inside the reverse sync.** `_finish_rollback` holds one package write
transaction for the whole sync, but each legacy write commits on its own connection. The
ownership transition is the last durable step: it runs only after that package transaction
(adoptions, the rollback watermark, applied deletions) has committed, so a crash or a failed
commit (for example a full disk, `StorageFull`) before it leaves `rollback_in_progress`, which
`resume` finishes. A crash or failure before the commit rolls back the package transaction,
including the `legacy_round_trip` marker and `LEGACY_IMPORT` source that `_write_back` adds to a
restored package-native record, while the restored legacy row stays committed. Before its first
legacy write, `_finish_rollback` therefore records every package record id in the cutover set, in
its own committed transaction (`legacy.record_rollback_ids`): a record a forget removes before the
rollback completes (while it is in progress or after it crashed, by cascade, with its evidence or
by any target) is deleted from the legacy store by the resumed rollback, whatever the legacy row
carries. Tests:
`tests/test_review_round3_batch1.py::test_mf1_a_forget_between_a_crashed_rollback_and_resume_reaches_the_legacy_copy`,
`::test_mf4_a_failed_package_commit_leaves_the_rollback_resumable`. A forget made while a rollback
is in progress, and not yet applied by it, carries the limitation that the legacy store still
holds the copy until the rollback is resumed (`ForgettingService.rollback_pending`). `_write_back` therefore adopts a package-native record whether or not the current pass
changed its legacy row: on `resume` the row already matches (counted `unchanged`) and the record
is adopted then, so a later `prepare_shadow` does not refuse its id. The adoption is idempotent
(nothing is rewritten when marker, legacy revision and fingerprint already match). Tests:
`tests/test_review_round2_batch2.py::test_fg7_a_resumed_rollback_adopts_package_native_records`
(a simulated crash and a real exception from the final transition). When the importer does refuse
a legacy id, `MigrationError.details` names the conflicting record ids (`ids`, at most 20).

### 4.11 Rollback

**Before cutover.** During `shadow_prepared` and `validated` the legacy vault remains the only
permitted writer. The migration tools open the legacy file only read-only: `legacy._connect_ro`
uses `mode=ro`, and the snapshot reads from a read-only source connection. Rolling back is
therefore only a state change:

- From `validated`, use `abort_cutover` (CLI: `migrate abort --yes`).
- From `shadow_prepared`, no Migrator method or CLI command returns to `legacy_authoritative`,
  although `TRANSITIONS` permits it. Legacy is still the permitted writer in that state.

The package-side copy remains, and the next import reconciles it. Tests:
`tests/test_migrations.py::test_crash_during_shadow_leaves_legacy_authoritative`, and
`tests/test_migrations.py::test_full_cutover_fences_legacy_writer`, in which legacy writes during
the shadow phase are accepted and imported.

**After cutover.** `Migrator.plan_rollback()` makes no record changes. Opening the legacy vault
(`LegacyMemoryVault(self.legacy_db, ...)`) may still change the file: `_initialize` runs
`CREATE TABLE IF NOT EXISTS`, adds missing columns to an old-format file, switches to WAL and
chmods the file to 0600. If the legacy file is missing, it creates an empty legacy vault (and
its parent directory). The plan reports:

- `representable`: records the legacy store can hold, including records it holds as absence;
- `unrepresentable`: counts by reason (section 4.12);
- `memory_tombstones` and `tombstones`;
- `legacy_rows_to_delete`: an upper bound, the number of legacy ids that are not in the set of
  readable package records. It also counts rows the rollback keeps (rows whose package record
  no longer authenticates, and legacy rows that do not decrypt). It reads 0 if the legacy file
  cannot be read;
- `safe`: true when nothing is unrepresentable. Damaged package records (see below) do not make
  the plan unsafe.

`Migrator.rollback(allow_partial=False)` then does this:

1. **Plan or refuse.** It requires `package_authoritative` and computes the plan. If the plan is
   not safe and `allow_partial` is false, it raises `MigrationError` (details:
   `unrepresentable`), and the state does not change.
2. **Fence.** It moves to `rollback_in_progress` and records `allow_partial`. From now on no
   writer is permitted.
3. **Hold the package write lock.** `_finish_rollback` holds the package partition's write lock
   for the whole sync. Package writers that passed the up-front fence wait for the lock. They
   are rejected with `OwnershipFenced` by `CoreService._check_owner` if they acquire it after
   the hand-back, or with `Contention` if the sync outlasts `Database.write`'s busy retries (by
   default four `BEGIN IMMEDIATE` attempts with a 5 s busy timeout each). Either way, nothing
   commits. A forget can still append its deletion-ledger entry meanwhile; that deletion wins
   (step 5).
   1. Apply pending deletion-ledger entries (`Migrator._apply_pending_deletions`).
   2. Read every package record and every legacy row. Package records that fail authentication
      are set aside as damaged (`Migrator._package_records`).
   3. **Delete what the package no longer has.** `Migrator._delete_gone` deletes the legacy rows
      of the cutover set (section 4.9, plus the ids this rollback writes back,
      `legacy.record_rollback_ids`) without a live package record: forgotten by any target, by
      cascade or with their evidence, or removed. A legacy row the package never held is deleted only when a package forget covers
      it (`legacy.forgotten_check`); otherwise it is kept and counted `legacy_only_kept`. (A
      cutover made by an earlier build recorded no set: then every legacy row without a package
      record is deleted.) A legacy row that does not decrypt is left untouched and counted
      `legacy_unreadable_kept`. The legacy row of a damaged package record is also left
      untouched, and no count reports it.
   4. **Walk the readable package records.** For each one:
      - **Absent in legacy:** effective lifecycle rejected or expired (TTL or retention passed at
        read time), or superseded without ever having been approved. Its legacy row is deleted.
      - **Unrepresentable** (normally only with `allow_partial`, since step 1 refuses otherwise;
        the sync does not re-check the flag): it is not written back and is counted
        `kept_in_package_only`. If it already had a legacy row (an imported record corrected,
        re-scoped or given transient retention after cutover, or a governed procedure written by
        an earlier rollback), that earlier version is deleted (`deleted_stale_unrepresentable`,
        `deleted_governed_procedures`): left in place, the authoritative legacy store would serve
        a corrected-away statement, durably. The ids join the rollback recovery set
        (`legacy.record_rollback_recovery`, replaced by every rollback): a re-migration never
        treats their missing legacy row as a legacy deletion, and an unchanged earlier legacy row
        of one (restored from a backup) never wins over the package record by drift repair
        (counted `recovery_kept`).
      - **Otherwise:** it is written back (see below).
   5. **Re-check deletions.** Deletions that arrived during the sync are applied, and
      `_delete_gone` runs again, until none remain (`Migrator._apply_late_deletions`).
   6. **Checkpoint.** `Migrator._checkpoint_legacy` runs `PRAGMA wal_checkpoint(TRUNCATE)` on the
      legacy file, so page images of deleted rows do not linger in the WAL. The legacy vault
      itself runs with `secure_delete=ON`. The checkpoint can wait seconds for legacy readers, so
      it runs before the next step.
   7. **Close the ledger.** A forget is never fenced and appends its ledger entry before it waits
      for the package write lock. So that no append falls between the last check and the hand
      back (it would then be applied to the package only, while the legacy store, authoritative
      again, keeps the row), the rollback takes the deletion ledger's write lock, which every
      append takes in any process, and holds it until the package transaction and then the
      hand-back have committed. Lock order is the one every writer uses: package store, then
      ledger (the ownership control store last). With the lock held, deletions are re-checked a
      last time, and the deletion generation reached is recorded as the rollback watermark
      (`legacy.record_rollback_watermark`): every forget up to it, of any target, is now applied
      to the legacy store (section 4.6). The package transaction commits here.
   8. **Hand back.** Only after that commit: move to `legacy_authoritative`, recording
      `package_readonly_recovery`, `rolled_back_at` and `rollback_deletion_generation` (the
      watermark). If the last check
      deleted rows, the legacy WAL is checkpointed again after the locks are released.

   A forget whose ledger append comes after the hand-back is a forget while legacy is the
   authority: it is applied to the package store, and its receipt carries a limitation saying
   the legacy store keeps serving its copy until it is forgotten there or the next cutover applies
   the deletion (`ForgettingService.legacy_store_keeps`; the same note is on any package forget
   while legacy is authoritative, before a first cutover too). Tests:
   `tests/test_review_round2_batch2.py::test_fg5_a_forget_appended_during_the_final_checkpoint_reaches_the_legacy_store`,
   `::test_fg5_no_forget_appends_between_the_final_check_and_the_transition`,
   `::test_fg5_receipts_say_whether_the_legacy_store_still_holds_the_memory`.
4. **Report.** The result holds `state`, `counts`, `package_readonly_recovery`,
   `package_only_ids` (the opaque ids kept in the package, at most 200) and `limitations`. The
   `counts` can contain these keys: `unchanged`, `written_back`, `restored`,
   `deleted_forgotten`, `deleted_rejected_or_expired`, `deleted_unapproved_superseded`,
   `deleted_governed_procedures`, `deleted_stale_unrepresentable`, `kept_in_package_only` and
   `legacy_unreadable_kept`. They come
   from a `Counter`, so a key is present only when its count is non-zero. No key counts damaged
   package records.

**Write-back (`Migrator._write_back`).**

- The record is compared with its existing legacy row: the stored fields (`_comparable`), the
  target hash, `superseded_by`, and a candidate's `expires_at`. If nothing differs, it is counted
  `unchanged`.
- Otherwise it is saved through `LegacyMemoryVault.save`, with the target hash overridden and,
  for a restored row, the original `created_at`. Direct SQL then sets `superseded_by` and a
  candidate's `expires_at`, because `save()` cannot set those columns.
- The legacy store assigns revisions as its own `save` does: 1 on insert, +1 on update.
- A package-native record written to legacy is marked `extra.legacy_round_trip`, gets a
  `LEGACY_IMPORT` source and records the written row's `legacy_revision` and metadata fingerprint
  (change `legacy_adopted`). Its own provenance (basis, citations, `derived_from`) is kept, here
  and by every later delta (section 4.4). A later migration adopts it instead of refusing its id,
  and propagates a legacy deletion of its row (section 4.5). The adoption runs even when the row
  was already up to date, so a resumed rollback adopts what an interrupted one wrote
  (section 4.10).

**What the write-back loses.**

- Unknown confidence is written as 1.0, the legacy default.
- The package's `updated_at` is not preserved. `LegacyMemoryVault.save` sets `updated_at` to the
  rollback time for every row it writes.
- Embeddings were dropped at import, so restored rows have none. An existing row whose title,
  content or tags changed also loses its cached embedding (the D24 rule in `save`). Legacy
  semantic recall needs the host to re-embed these rows.
- `use_count`, `last_used_at`, feedback counts, source session and run ids, and
  `last_confirmed_at` are not sent. Existing rows keep `created_at`, `use_count` and
  `last_used_at` (columns the `save` upsert does not touch), plus whatever the legacy `save`
  merge rules keep ([locus-compatibility.md](locus-compatibility.md) §4.10). Restored rows start
  without them.
- Package-only metadata has no legacy representation: statement basis, sources other than the
  legacy provenance, revision history, tombstones. Tombstones stay in the package store.
- `Migrator` accepts `project_workspaces`, but the rollback does not read it. The workspace
  target for a `project` scope comes from `LegacyMapping.workspaces`, which the CLI builds from
  `--workspace` (section 5.2).

### 4.12 Unrepresentable records and the `allow_partial` read-only recovery

`Migrator._legacy_shape`, `Migrator._unrepresentable_key` and `Migrator.plan_rollback` classify
the records that the legacy format cannot hold:

| Key in `plan.unrepresentable` | Cause |
|---|---|
| `governed_procedure` | A procedure record with a governed procedure payload (state, findings, evidence) |
| `retention:<policy>` | Retention policy `transient` or `session`, or a non-candidate with an expiry. In the legacy store it would become a permanent memory. |
| `<kind>:<dimensions or global>` | Kind `constraint`, `repository_observation`, `episode` or `summary`; or more than one scope dimension; or a single dimension other than `agent`, `legacy_target`, or a `project` that has a mapping entry (for example `fact:repository`) |
| `session_history_messages` | The partition holds session-history archive messages |

- **Without `allow_partial`:** the rollback is refused, and the state stays
  `package_authoritative`.
- **With `allow_partial`:** the rollback proceeds.
  - Unrepresentable records are not written back. They stay in the package store, counted
    `kept_in_package_only`.
  - The result sets `package_readonly_recovery: true` and adds the limitation that these records
    are not visible through the legacy API.
  - The ownership details record the same flag.

**Earlier legacy versions on the `allow_partial` path.** An unrepresentable record that already
had a legacy row (for example an imported record that was corrected or re-scoped after cutover,
or given transient retention) is not written back, and its legacy row - the pre-cutover version -
is deleted (`deleted_stale_unrepresentable`; `plan.stale_legacy_rows_to_delete` announces it), so
the legacy API serves neither version and the limitation text says so. A re-migration keeps the
package record (its correction and expiry) and does not forget it for its missing legacy row; a
legacy delta never brings back a suppressed (corrected-away, rejected) statement
(`skipped_suppressed`; verify reports the difference until it is resolved). Tests:
`tests/test_review_round3_batch2.py::test_mf8_a_partial_rollback_never_leaves_the_corrected_away_row_served`,
`::test_mf8_a_re_migration_keeps_the_correction_and_its_expiry`,
`::test_mf8_an_unchanged_earlier_legacy_row_never_wins_over_the_recovery_record`,
`::test_mf8_a_delta_never_brings_back_a_suppressed_statement`.

**Damaged package records.** Records that fail authentication are set aside by
`Migrator._package_records` in both `plan_rollback` and `_finish_rollback`. They are not counted
as unrepresentable, so `plan.safe` can be true. They are never written back, their legacy rows
are kept unchanged, and no count in the rollback result reports them.

**Session history and other unfenced writes.** The read-only recovery covers canonical memory
records only. `MemoryEngine.ingest_event` and other non-record writes are not fenced (section
3.3). `plan_rollback` counts every session-history archive message in the partition as
`session_history_messages`, which makes the plan unsafe. Messages ingested while legacy is
authoritative count too: the Stage-2 adapter archives messages with `LOCUS_MEMORY_ARCHIVE=1`
(handoff §4). If the cutover runs on a partition that holds such an archive, every later
rollback needs `allow_partial`.

**What "read-only" means here.** With legacy authoritative again:

- package canonical record writes are fenced, provided the host wires
  `HostCapabilities.ownership` (non-record writes are not; see above);
- maintenance skips lifecycle writes;
- reads still work, so the records can be recovered;
- forgetting still works.

Tests: `tests/test_migrations.py::test_rollback_refuses_unrepresentable_records_unless_partial`
(the episode is still readable through `MemoryEngine.get_episode` after a partial rollback),
`tests/test_review_group1.py::test_rollback_respects_package_expiry_and_retention`,
`tests/test_review_group1.py::test_rollback_keeps_governed_procedures_out_of_the_legacy_store`.

**Limitations.**

- The store is read-only only through the fence.
- Nothing bounds how long this recovery store is kept (R20.6: not implemented). The operator
  deletes it. (Snapshot directories are removed by a successful cutover, section 4.9.)

## 5. Legacy field mapping

The mapping runs in `legacy.map_record` (legacy -> package) and in `cutover.Migrator._legacy_shape`
and `_write_back` (package -> legacy). Legacy ids are kept, so a package record id equals its
legacy id.

### 5.1 Lifecycle

**Legacy to package** (`legacy.lifecycle_for`, evaluated at import time after timestamps are
normalized):

| Legacy `status` | Other legacy columns | Package lifecycle |
|---|---|---|
| `candidate` | `expires_at` is null or not yet passed | `candidate` |
| `candidate` | `expires_at` has passed | `expired` |
| `approved` | `superseded_by` is set | `superseded`, with `links.superseded_by` |
| `approved` | `stale = 1` and no `superseded_by` | `stale` |
| `approved` | neither | `approved` |

- **Status is checked first.** A candidate with `stale` or `superseded_by` set stays a candidate,
  or becomes expired.
- **Migration never approves.** Candidates are never approved by migration (R20.3).
- **No legacy "rejected".** Legacy rejection is a hard delete, so there is no rejected status to
  map. If an imported row is deleted, the next import tombstones it in the package (section 4.5).

**Package to legacy** (rollback; `_absent_in_legacy` uses the lifecycle that is effective at
rollback time):

| Package lifecycle | Legacy result |
|---|---|
| `candidate` | `status=candidate`, `expires_at` = the package expiry |
| `approved` | `status=approved`, `stale=0` |
| `stale` | `status=approved`, `stale=1` |
| `superseded`, approved at some revision (or imported as approved) | `status=approved`, `stale=1`, `superseded_by` set |
| `superseded`, never approved | row deleted or not written |
| `rejected` or `expired` (including TTL or retention passed at read time) | row deleted or not written |
| forgotten (no live package record) | row deleted, unless it does not decrypt |

### 5.2 Scope and target

**Legacy to package** (`legacy.LegacyMapping.scope_for`):

| Legacy `scope` / `target_hash` | Mapping entry | Package scope |
|---|---|---|
| `personal` / `personal` | none needed | global (no dimensions) |
| `workspace` / `workspace:<sha256 of the resolved path>` | `LegacyMapping.workspaces[<hash>]`, built from `--workspace PATH=PROJECT` with `compat.legacy_vault.legacy_workspace_hash` | `project=<id>` |
| `agent` / `agent:<sha256 of the agent id>` | `LegacyMapping.agents[<hash>]`, built from `--agent-id` with `legacy_agent_hash` | `agent=<id>` |
| `workspace` or `agent` with no mapping entry | none | `legacy_target=<target_hash>`. Only callers granted that legacy target can see it (CLI: `--legacy-target`). |

Notes:

- **Path resolution.** `--workspace PATH` is resolved (`expanduser().resolve()`) on the machine
  that runs the migration. It must resolve to the same string Locus resolved. Otherwise the
  records stay `legacy_target`-scoped, and `inventory` reports them under `unmapped_scopes`.
- **Mapping changes later.** If a mapping is added or changed after an import, the next import
  re-scopes the affected records (section 4.4).
- **Locus Stage 2.** The adapter maps every workspace hash to `ws-<hash[:32]>` and maps no
  agents, so agent records stay `legacy_target`-scoped (handoff §2, §8).

**Package to legacy** (`Migrator._legacy_shape`):

| Package scope | Legacy `scope` / `target_hash` |
|---|---|
| global | `personal` / `personal` |
| `legacy_target=workspace:...` or `legacy_target=agent:...` | `workspace` or `agent`, with that hash |
| `agent=<id>` | `agent` / `agent:<sha256 of the id>` |
| `project=<id>` with a mapping entry | `workspace` / `workspace:<hash from the mapping>` |
| `project` with no mapping entry, any other single dimension, or more than one dimension | unrepresentable (section 4.12) |

### 5.3 Other fields

| Legacy column or payload field | Package field |
|---|---|
| `id` | `MemoryRecord.id` (kept) |
| `revision` | `MemoryRecord.revision` at first import, and `extra.legacy_revision`. Later deltas give the package its own revisions (section 4.4). |
| `kind` (`preference`, `fact`, `decision`, `procedure`, `relationship`) | the same `MemoryKind`. Any other value becomes `fact`. `procedure` also gets `extra.legacy_ungoverned_procedure = true`, because it never passed procedural evaluation. |
| `title`, `content`, `tags`, `reason` | the same fields |
| `confidence` | `Confidence(value, calibrated=False, method="legacy_unspecified")` when finite and in [0, 1]. Otherwise unknown, with the note `invalid_confidence_dropped`. |
| (none) | `basis = StatementBasis.LEGACY` |
| `valid_from`, `valid_until` | `Validity`. A value that looks like milliseconds is divided by 1000. Other out-of-range or non-numeric values are dropped, and the raw value is kept in `extra.legacy_raw_<name>`. If `valid_until` is not after `valid_from`, `valid_until` is dropped. |
| `expires_at`, `pinned` | `Retention("durable", expires_at, pinned)` |
| `supersedes`, `superseded_by` | `Links.supersedes`, `Links.superseded_by` |
| `created_at`, `updated_at` | `created_at` and `event_time`; `updated_at`. `ingested_at` is the import time. |
| (every row) | source `SourceRef(LEGACY_IMPORT, "legacy-vault:<id>", actor=SYSTEM, locator={legacy_revision})` |
| `source_session_id`, `source_run_id` | `SourceRef(SESSION, ...)` and `SourceRef(TASK_ATTEMPT, ...)`, with `actor=HOST` and `available=False` |
| `status`, `scope`, `target_hash`, `stale` | also kept as `extra.legacy_status`, `legacy_scope`, `legacy_target_hash`, `legacy_stale` |
| metadata (section 4.4) | `extra.legacy_fingerprint` |

### 5.4 Unsupported fields

These come from `legacy.UNSUPPORTED_FIELDS`. `inventory` reports each one with its record count.

| Field | Handling |
|---|---|
| `embedding` | Dropped. Vectors can be re-derived and are model-specific; re-embed under provider consent. `extra.legacy_embedding_model` keeps the model name, and the note `embedding_dropped` is set. |
| `use_count` | Kept in `extra.legacy_use_count`. Never used for ranking or confidence. |
| `last_used_at` | Kept in `extra.legacy_last_used_at` |
| `feedback` | Kept in `extra.legacy_feedback` |
| `provenance` | Kept in `extra.legacy_provenance` if its JSON is at most 8,000 characters. Otherwise `extra.legacy_provenance_truncated` is set and the provenance is not kept. |
| `last_confirmed_at` | Kept in `extra.last_confirmed_at` |

### 5.5 Tables not migrated

These come from `legacy.NOT_MIGRATED_TABLES`. `inventory` reports their row counts.

| Table (same SQLite file, same key) | Handling |
|---|---|
| `memory_events` | Content-free diagnostics. They stay in the legacy file and are not copied, except that a snapshot copies the whole file. |
| `context_snapshots` | A separate ownership family (`context_snapshots`). It stays `legacy_authoritative`. This importer does not migrate it, and no other importer exists. |
| `skill_observations` | A separate ownership family (`skill_observations`). Same as above. |

Moving the two continuity families into package ownership is a Stage-3 item (handoff §9, item 4).
Until it is done, `compat.legacy_vault.LegacyContinuityStore` serves them. They share
`memory.sqlite3` with the `memories` table, so the legacy file cannot be retired while they are
legacy-owned.

This protocol does not cover the older plaintext workspace-note migration. That one moves notes
into the *legacy* vault (Locus `memory_runtime.py`; at the inspected commit it uses its own
implementation, and with the Stage-1 patch it delegates to
`LegacyMemoryVault.import_legacy_note`; tests:
`tests/test_compat_legacy.py::test_legacy_note_import_is_crash_safe_and_preserves_created_at`).

## 6. CLI commands (`locus-memory migrate ...`, defined in `src/locus_memory/cli.py`)

**Global options** go before the subcommand:

- `--root`, `--profile`, `--edition`, `--key-dir`;
- scope grants, each repeatable: `--project`, `--repository`, `--worktree`, `--agent`, `--team`,
  `--session`, `--device`, `--legacy-target`;
- `--admin` and `--json`, which are also accepted after the subcommand.

**Legacy options** (`cli._add_legacy_options`):

- `--legacy-db PATH`: required; must be an existing file.
- `--key-file PATH`: required; the legacy `master.key` as 32 raw bytes or 64 hex characters.
- `--workspace PATH=PROJECT`: repeatable.
- `--agent-id ID`: repeatable.
- `--work-dir DIR`: required for `import`, `verify`, `cutover` and `rollback`. `inventory` does
  not accept it.

**Exit codes:** 0 ok, 1 error, 2 preview only (nothing changed), 3 capability unavailable, 4 storage
unavailable (disk full, read-only files, I/O error).

| Command | Requires | What it does | Exit codes |
|---|---|---|---|
| `migrate inventory <legacy options>` | Nothing: no `--admin`, no initialized profile | Read-only counts (section 4.1). Does not create the store root. | 0, 1 |
| `migrate snapshot --legacy-db PATH --out DIR` | No admin, no key, no profile | Snapshot and manifest in a new directory (section 4.2). The CLI prints the number of row fingerprints, not the fingerprints. | 0, 1 |
| `--admin migrate import <legacy options> --work-dir DIR` | Admin; an initialized profile (otherwise `not_initialized`); state `legacy_authoritative` | `Migrator.prepare_shadow`. Creates `<root>/control.sqlite3`. | 0, 1 |
| `--admin migrate verify <legacy options> --work-dir DIR [--query Q]...` | Admin; profile | In `shadow_prepared`: `Migrator.validate`, a delta import that moves to `validated` when verify passes. In any other state: read-only `legacy.verify`. | 0 when verification passes, 1 when it fails |
| `--admin migrate state` | Admin | Ownership row and transition history for this profile's `memories` family | 0 |
| `--admin migrate cutover <legacy options> --work-dir DIR [--query Q]... [--yes]` | Admin; `validated`, or `cutover_in_progress` (then it resumes) | Preview without `--yes`. With `--yes`: section 4.9. Passes no quiesce hook. | 2 preview; 0 if the state ends `package_authoritative`; 1 if the cutover aborted to legacy or failed |
| `--admin migrate abort [--yes]` | Admin; `validated` or `cutover_in_progress` | `abort_cutover` | 2 preview; 0; 1 |
| `--admin migrate rollback <legacy options> --work-dir DIR [--allow-partial] [--yes]` | Admin; `package_authoritative`, or `rollback_in_progress` (then it resumes with the recorded `allow_partial` and ignores the flag) | Preview without `--yes`; in `package_authoritative` the preview includes `plan_rollback`. With `--yes`: section 4.11. | 2 preview; 0; 1 (a refusal is error `migration_error`) |

Notes on the commands:

- **Resuming.** There is no separate `resume` subcommand. Run `cutover --yes` or `rollback --yes`
  again; in an in-progress state they resume.
- **Missing legacy file.** If the state is `cutover_in_progress` and the `--legacy-db` file is
  missing, `migrate cutover` aborts to `legacy_authoritative` instead of resuming. Without
  `--yes` it previews that abort (exit 2); with `--yes` it aborts (exit 0).
- **The profile's own writes are fenced.** Once a profile has a recorded transition, the CLI
  fences that profile's package canonical writes (`remember`, `propose`, ...) until cutover
  completes, and again after a rollback. The CLI test checks that `remember` returns
  `ownership_fenced` in `shadow_prepared`.
- **Grants.** Scope grants do not limit what is imported. They limit what the invocation can
  read afterwards, and what the `--query` retrieval comparison can see.
- **Rehearsal only.** The CLI opens the profile with its own standalone file key (`--key-dir`).
  It is not wired to the Locus key provider (`LocusKeyProvider` in patch 0002). A Locus cutover
  would run `Migrator` in-process from the host, as handoff §9 describes. The CLI is for
  rehearsing the protocol.

**Rehearsal on a disposable copy.** This follows the snapshot, import, verify, cutover and
rollback sequence of `tests/test_cli.py::test_migrate_snapshot_and_full_cutover_flow`, which
runs against the synthetic fixture. The inventory and abort steps are not part of that test.
The test also runs checks this rehearsal omits: `not_initialized` and `access_denied` errors,
`remember` while fenced, `show`, and a read-only `verify` after cutover. Run the rehearsal only
on a disposable copy. A WAL-mode vault needs a consistent copy, for example
`sqlite3 SRC ".backup DST"`; copying only the main file can miss committed rows. Making the copy
from real Locus data is itself a real-data action, and requires authorization (R0.3).

```sh
W=/tmp/lm-rehearsal                                   # disposable working directory
LEG=(--legacy-db "$W/legacy/memory.sqlite3" --key-file "$W/legacy/master.key"
     --workspace "/path/to/workspace-a=proj-a" --agent-id agent-1)
G=(--root "$W/store" --project proj-a --agent agent-1 --admin)

locus-memory migrate inventory "${LEG[@]}"                                       # read-only, counts only
locus-memory migrate snapshot --legacy-db "$W/legacy/memory.sqlite3" --out "$W/snap-check"
locus-memory --root "$W/store" init                                              # the profile must exist
locus-memory "${G[@]}" migrate import   "${LEG[@]}" --work-dir "$W/work"         # -> shadow_prepared
locus-memory "${G[@]}" migrate verify   "${LEG[@]}" --work-dir "$W/work" --query "tabs"   # -> validated
locus-memory "${G[@]}" migrate cutover  "${LEG[@]}" --work-dir "$W/work"         # preview, exit 2
locus-memory "${G[@]}" migrate cutover  "${LEG[@]}" --work-dir "$W/work" --yes   # -> package_authoritative
locus-memory --root "$W/store" --admin migrate state
locus-memory "${G[@]}" migrate rollback "${LEG[@]}" --work-dir "$W/work"         # preview with plan, exit 2
locus-memory "${G[@]}" migrate rollback "${LEG[@]}" --work-dir "$W/work" --yes   # -> legacy_authoritative
locus-memory --root "$W/store" --admin migrate abort                             # preview; only valid in validated or cutover_in_progress
```

Add `--json` to any command to get exactly one JSON document on stdout. The array syntax works in
both bash and zsh.

## 7. Migration artifacts and plaintext

| Artifact | Location | Contents | Protection |
|---|---|---|---|
| Ownership control | `<root>/control.sqlite3` | States, generations, timestamps, reasons, `details` (including the snapshot directory path) | Mode 0600. Plaintext metadata with no record content. |
| Snapshot | `<work_dir>/snapshot-<ms>/legacy-snapshot.sqlite3` | A copy of the legacy file: the same ciphertext and the same plaintext metadata columns | Mode 0600 |
| Manifest | `<work_dir>/snapshot-<ms>/manifest.json` | Row ids, row fingerprints, the snapshot hash | Process umask; no record content |
| Package partition | `<root>/<partition id>/...` | Migrated records | Encrypted at rest (README) |

Plaintext canary tests:

- `tests/test_migrations.py::test_migration_artifacts_contain_no_plaintext` scans the migration
  work directory and the engine root.
- `tests/test_cli.py::test_migrate_snapshot_and_full_cutover_flow` scans the snapshot directory
  right after `migrate snapshot`, for every fixture record's content. It scans the store root
  and the work directory after the rollback, for one record's content only.

A successful cutover removes the snapshot directories the migration wrote (and any later forget or
open retries a removal that failed). A snapshot of a migration that never reached cutover stays
until the operator deletes it, and nothing prunes a partial-rollback recovery store.

## 9. What was not done

- **No real data was migrated.** No `migrate` command and no `Migrator` method has run against a
  real Locus `APP_DIR`. Every run used disposable copies of the synthetic fixture
  `tests/fixtures/locus_legacy/memory.sqlite3`.
- **No cutover or rollback ran in Locus**, in the disposable copy or anywhere else. The Stage-1
  and Stage-2 host tests cover code extraction and the derived copy, with the legacy vault
  canonical. Stage 1 has no ownership control. Stage 2 creates one with no recorded transition,
  so it reads `legacy_authoritative`.
- **Nothing reached the real Locus checkout.** The handoff patches were not applied to it, no
  host feature was enabled, and nothing was published or pushed.
- **No host-side cutover wiring exists**: no quiesce hook, no `write_guard` on the legacy vault,
  and no redirect of host reads and writes at cutover.
- **Other stores are not migrated**: no migration for `context_snapshots`, `skill_observations`,
  `memory_events`, or the other memory-bearing stores in the ownership inventory.
- **No retirement step**, and no pruning of a partial-rollback recovery store (section 8).
- **Untested paths:**
  - the `after_rollback_fence` crash point, and the other interruption boundaries listed in
    section 4.10 (R20.4 is only partly covered);
  - a non-null quiesce hook, including a failing one;
  - an unguarded legacy writer during cutover;
  - the rollback's own WAL checkpoint (`Migrator._checkpoint_legacy`);
  - migration performance at host vault sizes. [evaluation.md](evaluation.md) has no migration
    measurements.
- **Open gaps, confirmed by code reading and by probes on disposable fixture copies, not fixed:**
  - with `allow_partial`, an unrepresentable record that already had a legacy row leaves its
    pre-cutover version in the legacy store, so its post-cutover corrections are not preserved
    there (section 4.12).
- **Open gaps, from code reading only:**
  - damaged package records are set aside by the rollback without being counted or reported
    (section 4.12);
  - read-path side effects of a guarded legacy vault are checked only up front, outside a
    guarded transaction (section 3.3);
  - the session-history archive and other non-record writes are not fenced, and any archived
    history makes every rollback plan unsafe (section 4.12);
  - the `verify` retrieval comparison ignores scope and grants on the legacy side (section 4.7).
